# 在有限资源下搭建 RAG Web 服务：从文档解析到检索问答

RAG 的概念并不复杂：先从知识库中检索相关内容，再让大模型基于这些内容回答问题。真正困难的是把这条链路做成一个可以长期运行的 Web 服务，尤其当部署环境只有有限的 CPU、内存和磁盘时，每一个组件都需要有明确的边界。

与其一开始追求复杂架构，我更倾向于先完成最小闭环，再用可观测数据决定是否增加组件。

## 最小可用链路

一个面向个人或小团队的 RAG 服务，可以先拆成六个步骤：

1. 上传 PDF、Word、Markdown 或 XMind 等资料；
2. 解析正文并保留文件名、页码、标题层级等来源信息；
3. 按语义和长度切分文本；
4. 生成向量并写入索引；
5. 根据问题召回相关片段；
6. 把片段连同引用信息交给模型生成答案。

最小版本不必急着加入多租户、复杂权限或分布式队列，但必须从第一天保留任务状态和错误信息。上传成功不等于入库成功，用户应该能看到文件正在解析、已完成还是失败，以及失败发生在哪一步。

## 文档解析决定知识上限

许多 RAG 问题最终不是模型问题，而是文档在进入向量库之前已经丢失结构。PDF 可能存在双栏、页眉页脚和扫描图片；Word 包含表格与层级标题；XMind 更接近树形数据。如果所有内容都被简单拼成一段文本，检索时就很难恢复上下文。

解析层应输出统一的数据结构，例如：

```json
{
  "source": "network-plan.pdf",
  "section": "3.2 回归策略",
  "page": 12,
  "text": "……",
  "content_type": "paragraph"
}
```

统一结构让后续切分、索引和引用展示不必理解每一种原始格式。对于无法可靠解析的文件，应明确标记并允许重新处理，而不是静默写入空内容。

## 切分不是固定字数

固定长度切分容易实现，但会切断标题与正文、步骤与解释之间的关系。更稳妥的策略是先按文档结构分段，再对过长段落做二次切分，同时保留适度重叠。

切分参数需要结合评估问题调整。片段过短，答案缺少上下文；片段过长，会占用模型窗口并稀释关键信息。起步时可以把每个片段控制在数百个中文字符，并保留标题路径。之后观察“正确片段是否进入 Top K”，再决定长度，而不是直接复制某个框架默认值。

## 检索与生成要分开评估

当回答错误时，首先要判断正确证据是否被召回。如果 Top K 中没有正确片段，应该优化解析、切分或检索；如果证据已经存在但回答仍然错误，才需要检查提示词、上下文组织或模型能力。

我会维护一组固定问题，并为每个问题标注期望来源。最初不必追求复杂指标，可以记录：

- 正确来源是否出现在 Top K；
- 最终回答是否包含来源引用；
- 没有证据时是否明确拒答；
- 同一问题重复运行是否保持基本一致；
- 平均响应时间和峰值内存。

这些指标能够把“换模型试试”变成有依据的工程决策。

## 有限资源下的取舍

资源紧张时，最重要的不是把所有模型放在同一台服务器，而是明确哪些能力必须本地运行。嵌入模型通常比生成模型轻量，可以本地常驻；生成模型可以根据隐私和成本选择本地小模型或外部接口。

向量索引也不必一开始就引入独立数据库。数据量较小时，FAISS 配合结构化元数据已经能够完成验证。随着文档规模、并发和过滤需求增加，再评估专用向量数据库。

服务层应设置上传大小、并发任务数、模型超时和上下文长度上限。对于耗时解析，采用后台任务并在前端轮询状态，避免请求长期占用。缓存可以优先用于文档哈希、嵌入结果和高频查询，而不是盲目缓存所有回答。

## 安全与可维护性

RAG 服务处理的是用户资料，默认需要考虑文件隔离、类型校验、路径安全和日志脱敏。Markdown 渲染应关闭或净化危险 HTML；下载与引用接口不能接受任意文件路径；删除文档时要同时清理原文件、片段、向量和缓存。

同时，为模型提示增加清晰边界：只根据提供的上下文回答，忽略文档中试图改变系统规则的指令，并在证据不足时说明无法确认。它不能消除所有提示注入风险，但能减少知识库内容直接控制应用行为的机会。

## 从 Demo 到可用产品

一个可靠的 RAG 产品并不取决于组件数量，而取决于链路是否透明。用户能够知道资料是否处理成功，开发者能够看到每次回答用了哪些证据，系统能够在资源不足时稳定降级，这些往往比更大的模型更重要。

我的实现顺序会保持克制：先完成解析、检索、引用和评估闭环，再逐步加入重排、混合检索、对话记忆与权限。每增加一个组件，都必须回答它解决了哪一个已经被数据证明的问题。
