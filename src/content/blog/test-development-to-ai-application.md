# 从测试开发到 AI 应用开发：一条工程化成长路径

测试开发和 AI 应用开发看起来像两条不同的职业路线：前者强调质量、自动化和稳定性，后者关注模型、数据与产品能力。但真正进入工程现场后会发现，两者解决的是同一类问题——如何把不稳定、不可控的输入，转化为可重复、可观测、可交付的系统。

我更愿意把这次方向变化理解为一次能力迁移，而不是从零转行。测试开发积累的工程习惯，恰好能补足许多 AI Demo 在进入真实环境时暴露出的短板。

## 可以直接迁移的能力

### 1. 把模糊问题变成可验证条件

测试工作的第一步通常不是执行用例，而是定义“什么叫正确”。AI 应用同样如此。一个回答看起来合理，不代表它可靠；一个检索结果包含关键词，也不代表它真正支持最终结论。

因此，在开始接模型之前，我会先写出最小验收标准：

- 输入支持哪些格式，失败时如何提示；
- 回答是否必须引用来源；
- 检索不到内容时是否允许模型自由发挥；
- 响应时间、资源占用和并发上限是多少；
- 哪些结果需要人工确认。

这些标准让“效果不错”变成可以持续回归的工程目标。

### 2. 自动化与可重复性

测试开发长期面对环境差异、依赖漂移和偶现问题。AI 应用则多了模型版本、提示词、向量模型、切分策略与采样参数等变量。如果没有版本记录，同一个问题今天和明天可能得到完全不同的结果。

一个最小的实验记录至少应该包含：数据集版本、嵌入模型、生成模型、提示词版本、检索参数和评估结果。它不一定需要复杂平台，最初可以是一份结构化 JSON：

```json
{
  "dataset": "feedback-v3",
  "embedding": "bge-m3",
  "top_k": 5,
  "prompt_version": "qa-2026-08-01",
  "metrics": { "hit_rate": 0.82, "citation_rate": 0.94 }
}
```

只要能够稳定复现，后续才有优化的基础。

### 3. 故障定位与可观测性

AI 应用的错误往往不是一次异常栈，而是一个结果“不够对”。这要求系统暴露完整链路：原始问题如何改写、命中了哪些文档、每个片段的分数是多少、最终提示词由什么组成、模型用了多少时间。

测试开发中常用的分层定位思路仍然有效：先区分输入、检索、排序、生成和展示层，再用最小样本验证每一层。没有这些证据，调参容易变成凭感觉试错。

## 需要主动补齐的新能力

工程经验并不能替代 AI 基础。转向 AI Application Development 时，我把学习重点拆为四层。

第一层是模型调用与提示设计。目标不是收集提示词技巧，而是理解上下文长度、结构化输出、工具调用、流式响应和失败重试。

第二层是数据与检索。需要掌握文档解析、切分、嵌入、向量索引、混合检索和重排，并理解不同选择如何影响召回与成本。

第三层是应用工程。包括鉴权、任务队列、缓存、日志、评估、前端交互和部署。模型只是应用中的一个依赖，而不是整个系统。

第四层是产品判断。要明确 AI 在流程中的角色：是生成候选、提供辅助、执行自动化，还是直接做决策。角色越靠后，验证与兜底要求越高。

## 用项目构建学习闭环

只学习框架很容易陷入“会调用但不会交付”。更有效的方法是选择一个真实问题，做出能够被自己长期使用的最小产品。例如用户反馈分析平台或个人知识库，都可以形成完整闭环：

1. 收集真实但可公开的样本；
2. 完成上传、解析、检索和回答；
3. 为关键结果保留来源和日志；
4. 建立二十到五十条固定评估问题；
5. 部署到资源有限的环境并记录瓶颈；
6. 根据数据，而不是主观印象迭代。

每一次迭代都应该同时产生三类资产：可运行的代码、可解释的评估结果，以及一篇能够复盘决策的技术记录。这样，项目不仅展示“用了哪些技术”，还展示如何权衡和解决问题。

## 我的阶段性路线

近期我会继续以 Python 为主线，把已有的后端、前端和 Linux 经验串起来。短期目标是稳定完成 RAG Web 服务与 AI 工作流；中期目标是把评估、监控和部署纳入默认架构；长期则希望具备从问题定义到产品上线的 AI 全栈交付能力。

这条路线不会否定测试开发经历。相反，质量意识、自动化能力和复杂问题定位，是我进入 AI 应用开发时最有价值的起点。模型能力不断变化，但可靠交付的方法仍然可以沉淀。
